# 对话控制与习惯学习

## 对话系统映射

| 控制论概念 | 对话中的含义 | 典型观测 |
| --- | --- | --- |
| 目标值 | 用户期望的结果和质量门槛 | 明确需求、验收条件、示例 |
| 状态 | 当前已知事实、进度、错误和未决项 | 文件、工具输出、对话记录 |
| 控制量 | 能改变结果的下一动作 | 提问、编辑、测试、重试、回退 |
| 输出 | 用户可以观察和验证的结果 | 界面、安装包、文件、回答 |
| 误差 | 当前输出与目标之间的偏差 | 否定、纠正、失败日志 |
| 扰动 | 不属于计划但影响结果的因素 | 网络错误、权限、版本差异 |
| 时滞 | 动作与可见反馈之间的延迟 | 构建时间、浏览器刷新、人工验证 |
| 噪声 | 不应改变长期模型的弱信号 | 重复消息、口误、偶发失败 |
| 稳定性 | 扰动后仍能回到可接受状态 | 重启、重复操作和环境变化后仍正确 |
| 自适应 | 根据可靠反馈更新策略 | 偏好反复出现后固化为规则 |

先填写 `operational-control-model.md` 中的控制表。控制表回答当前任务如何闭环，本文件回答哪些对话信号值得进入长期模型。

## 状态向量

分析时维护以下状态，不需要向用户逐项展示：

```text
sample_scope: 本次学习的对话范围
goal: 最终目标与验收条件
current: 当前已完成和未完成内容
observations: 已验证事实
assumptions: 待确认假设
constraints: 必须遵守的边界
knowledge: 按五类知识归档的候选规则
evidence: 支持、反证、范围和置信度
errors: 已观察到的偏差和失败
actions: 可执行控制动作
delays: 尚未返回结果的动作
lifecycle: 规则和 Skill 当前状态
exit: 完成、复审或阻塞条件
```

每轮只更新发生变化的部分。已经验证的事实不要因模型猜测而降级，尚未验证的假设不要升级为事实。

## 知识分类

提取规则前先分类：

- 用户跨任务协作方式归入 `preference`。
- 产品应保持的行为归入 `product-rule`。
- 由源码、文件或运行态验证的事实归入 `architecture`。
- 数据保护、权限和发布边界归入 `safety-policy`。
- 暂时无法判断的推断归入 `hypothesis`。

不同类型不能仅因为写在同一段对话里就使用相同有效期。详细生命周期读取 `evidence-and-lifecycle.md`。

## 习惯证据等级

### A 级：可以形成稳定规则

- 用户明确说明“以后、总是、默认、必须、不要再出现”。
- 同一偏好在多个独立任务中重复，并且后续没有反向纠正。
- 用户明确确认某套流程应作为长期模板。

### B 级：需要组合证据

- 用户对具体结果满意，但没有说明是否长期适用。
- 同一纠正在同类任务中出现两次。
- 用户选择了某个方案，同时存在明显场景限制。

两个相互独立的 B 级证据可以升级为有范围的活动规则。升级时记录反证，不能扩大适用场景。

### C 级：只作为当前任务约束

- 单次命令、文件名、版本号、目录和临时截止时间。
- 因当前机器、网络、权限或第三方软件导致的限制。
- 模型根据语气、身份或沉默作出的推测。

C 级证据不得单独进入长期 Skill。

## 正反馈与负反馈

- 正反馈回答“哪条轨迹值得复用”，例如用户确认结果符合预期并在后续采用。
- 负反馈回答“偏差在哪里、应该如何纠正”，例如动作语义错误应转化为可测试的行为差异。
- 沉默不是正反馈；网络断开不是内容负反馈；重复发送不能计作多次独立证据。
- 纠偏规则采用“触发条件 -> 禁止动作 -> 替代动作 -> 验证信号”的格式。

示例：

```text
触发条件：用户要求验证安装版行为。
禁止动作：只修改源码后声称问题已解决。
替代动作：构建或取得目标安装包，在安装程序中执行用户路径。
验证信号：安装版本、实际界面和目标功能结果一致。
```

## 冲突反馈

- 先检查两条相反要求是否属于不同场景，不把条件变化误判为用户反复无常。
- 当前任务服从最新明确要求，长期规则保留旧证据和新反证。
- 能明确场景时生成条件规则；不能明确时降级为 `hypothesis`。
- 连续两次独立反向反馈触发 `stale`，停止隐式使用旧规则。

## 闭环更新算法

1. 确定样本范围和用户最新目标。
2. 填写目标、状态、观测、控制、扰动、时滞和稳定条件。
3. 从工具和对话中提取事实，按五类知识归档。
4. 为候选规则收集支持、反证和适用范围。
5. 计算当前结果与目标偏差，区分内容误差、执行误差和环境扰动。
6. 选择最小且能产生清晰反馈的控制动作。
7. 等待真实反馈并更新模型；重复失败时改变控制路径。
8. 只有证据达到门槛时才更新活动规则和候选 Skill。
9. 写入证据清单并执行前向评估，再决定生命周期状态。

## 防止过度拟合

- 把偏好限定在被观察到的场景，不从一个按钮推广到所有界面。
- 保存动作规则，不保存对用户人格的评价。
- 把产品规则和架构事实从个人偏好中分离。
- 将例外条件和适用边界与规则一起保存。
- 对冲突要求优先形成条件分支，不强行生成全局结论。
- 定期合并重复规则，标记被替代规则，不静默抹除判断历史。

## 隐私过滤

在写入候选 Skill 前，替换或删除：

- API key、token、密码、cookie 和认证链接。
- 邮箱、手机号、账号、精确地址和私人身份信息。
- 本地绝对路径、临时文件路径和仅当前机器有效的进程信息。
- 与规则无关的完整原始对话。

保留对行为有意义的抽象，例如把具体路径改为“项目工作区”，把具体账号改为“目标远端账号”。证据清单也必须执行同样的隐私过滤。
