# 证据账本与规则生命周期

## 五类知识

| 类型 | 含义 | 典型复审触发 |
| --- | --- | --- |
| `preference` | 用户稳定的协作或输出偏好 | 明确反向反馈、跨项目变化 |
| `product-rule` | 产品应保持的行为不变量 | 产品语义或需求变更 |
| `architecture` | 由源码和运行环境验证的当前事实 | 依赖、目录、IPC 或打包变化 |
| `safety-policy` | 数据、权限和外部副作用边界 | 权限模型或明确授权变化 |
| `hypothesis` | 证据不足的候选推断 | 获得新证据后升级或丢弃 |

不要把产品事实写成“用户喜欢”，也不要把安全政策伪装成对用户性格的判断。

## 证据等级

### A 级

- 用户明确声明长期规则，并且没有后续冲突。
- 同一规律在多个独立任务中重复出现，且后续继续采用。
- 高风险纠偏被明确要求永久避免，并能写出验证信号。

### B 级

- 同一纠正在同类任务中出现两次。
- 用户选择某方案，但适用场景有限。
- 工具或源码提供强事实证据，但该事实可能随版本变化。

两个独立 B 级证据可以形成有范围的活动规则。不得把同一事件的重复消息计算为两个证据。

### C 级

- 单次命令、版本、文件名、路径、截止时间或当前机器状态。
- 网络、权限、第三方服务和偶发系统故障。
- 根据语气、身份或沉默作出的推测。

C 级证据只进入当前任务或 `hypothesis`，不得单独成为长期规则。

## 活动规则记录

每条规则至少记录：

```json
{
  "id": "stable-rule-id",
  "type": "preference",
  "confidence": "high",
  "scope": "适用场景",
  "evidence_summary": "脱敏后的独立证据摘要",
  "counterevidence": "没有则写 none",
  "verification": "如何判断规则被正确执行",
  "review_when": "何时重新审查"
}
```

不保存完整原始对话、账号、路径或私人信息。需要追溯时使用抽象场景，不引用敏感原句。

## 冲突处理

1. 用最新明确指令控制当前任务。
2. 检查冲突是否来自不同场景，例如“复制”和“粘贴”可能是两个任务目标，而非永久偏好改变。
3. 能写出条件时生成分支规则；不能区分时保留反证并降级为 `hypothesis`。
4. 不静默删除旧证据，也不因为旧规则存在而拒绝当前明确指令。

## 时间、衰减与滞环

- 活动规则不会仅因时间经过自动删除，但长时间未出现且产品环境已变化时应复审。
- 同一规则连续出现两次明确反向反馈时，状态从 `active` 降为 `stale`。
- `stale` 规则不能隐式控制任务；只有重新获得稳定证据后才能恢复。
- 架构规则在相关源码或打包方式变化后立即转为“需重新验证”。
- 使用升级和降级的不同门槛形成滞环，避免规则随单次样本反复切换。

## 生命周期

```text
hypothesis -> candidate -> reviewed -> active -> stale -> deprecated
```

- `hypothesis`：证据不足。
- `candidate`：结构完整，尚未通过前向评估。
- `reviewed`：用户或独立检查确认规则范围。
- `active`：验证通过，可用于实际任务。
- `stale`：环境或反馈变化，需要复审。
- `deprecated`：已被明确替代，保留原因但不再触发。

## generation-manifest.json

证据驱动生成的 Skill 应在 `extras/generation-manifest.json` 保存：

- `schema_version`、`skill_name`、`generated_by` 和 `status`。
- 样本范围的脱敏描述。
- 活动规则及五类知识分布。
- 被过滤的 C 级信号。
- 冲突主题和条件化解决方式。
- 前向测试结果或未完成原因。
- 下次复审触发条件。

清单用于审查和维护，不应成为主 Skill 的长篇上下文。
